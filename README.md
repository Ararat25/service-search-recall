# Отбор кандидатов для поиска услуг: полнота 50

## 1. Задача
По короткому поисковому запросу нужно отобрать из корпуса (около 189 тысяч
объявлений) до 50 объявлений, которые дальше передаются на ранжирование.
Поиск устроен каскадом: если нужное объявление не попало в эти 50, вернуть его
уже нельзя. Поэтому главное требование здесь — полнота, а не порядок.
Качество измеряется метрикой Recall@50: для каждого запроса считается доля
подходящих объявлений, попавших в отобранные 50, затем значение усредняется
по всем запросам. Порядок объявлений внутри ответа на метрику не влияет.

## 2. Как устроено решение
Финальный скрипт — `scripts/make_answer_v4.py`. Для каждого запроса строится
восемь списков кандидатов, которые затем объединяются.

Четыре списка строятся методом BM25 (поиск по совпадению слов с учётом частоты).
Перед поиском слова приводятся к основе, чтобы сходились словоформы
(«домофонов» и «домофон»). Тексты объявлений берутся в двух видах: полный
(заголовок, повторённый трижды, плюс описание и параметры) и короткий
(заголовок дважды плюс параметры). Запрос ищется в четырёх вариантах:
исходный запрос по полному тексту (1200 кандидатов), запрос, дополненный
словами из объявлений, которые раньше выбирали по такому же запросу (500),
запрос, дополненный словами из трёх первых найденных объявлений (400),
исходный запрос по короткому тексту (300).

Ещё четыре списка строятся методом TF-IDF (взвешивание слов по частоте
в документе и редкости в корпусе): по отдельным словам и парам слов на
коротком тексте (600), по отдельным словам на полном тексте (400),
по сочетаниям из 3–5 букв на заголовке (600) и по сочетаниям из 3–4 букв
на коротком тексте (400). Буквенные сочетания ловят окончания, опечатки
и сложные слова («газелей» и «ГАЗель»).

Отдельно берутся кандидаты из истории выборов в обучающей выборке: сначала
объявления по точному совпадению текста запроса и города, затем по совпадению
только текста, затем объявления по трём похожим запросам из истории.

Слияние идёт в таком порядке: сначала кандидаты из истории, затем списки
объединяются поочерёдно (по одному объявлению из каждого списка — так набор
получается разнообразнее, чем при сортировке одним весом). Внутри объединённого
набора сначала идут объявления из того же города, что и запрос, среди них —
сначала объявления из той же подкатегории. Итог обрезается до 50.

## 3. Данные и признаки
Используются только три выданных файла в формате parquet (см. раздел 7).

| Что использовано | Как | Почему так |
|---|---|---|
| Заголовок объявления | отдельный поиск плюс утроенный вес в полном тексте | заголовок короткий (в среднем 34 символа) и точный; в склейке с длинным описанием (медиана 1054 символа) он теряется, поэтому ищется отдельно |
| Описание объявления | входит в полный текст | даёт покрытие: по верхней оценке лексика по всем полям находит 0.965 релевантных пар против 0.817 только по заголовку (файл `ceiling_report.txt`) |
| Параметры объявления | входят в короткий и полный тексты | короткие структурированные сведения («вид услуги»), информативны |
| Город запроса и объявления | объявления из того же города идут первыми, но чужие не отбрасываются | 83 процента релевантных — из того же города; жёсткий фильтр дал бы потолок 0.818 и отсёк бы 17 процентов релевантных из других городов; упорядочивание даёт прирост 0.17 к голому BM25 |
| Подкатегория объявления | приоритет внутри своего города | слабый сигнал, прирост 0.004 поверх географии; город важнее категории |
| История выборов из обучения | точные и похожие запросы дают готовые идентификаторы и слова для дополнения запроса | 907 из 2452 запросов бенчмарка дословно встречаются в обучении; но их идентификаторы в 95 процентах случаев отсутствуют в корпусе, поэтому история используется ещё и как текст, а не только как готовые ответы |
| Не использованы: цена, рейтинг, число отзывов, координаты, флаги телефона | — | это признаки для упорядочивания, а порядок метрикой не считается; они только занимали бы место в ответе |

Нормализация текста везде одинаковая: нижний регистр, замена «ё» на «е»,
удаление лишних символов. Для BM25 слова приводятся к основе, для TF-IDF
берутся как есть — разные обработки дают разные, дополняющие друг друга наборы.

## 4. Алгоритмы
BM25 считает вес документа по словам запроса с учётом частоты слова
в документе и редкости в корпусе, с поправкой на длину документа.
Библиотека `bm25s`, разреженный формат, два индекса (полный и короткий тексты).
TF-IDF — похожий подсчёт без поправки на длину, библиотека `scikit-learn`:
словарные модели (отдельные слова и пары слов) и буквенные модели
(сочетания букв с привязкой к границам слов). Всего восемь списков:
два индекса BM25 на три варианта запроса плюс четыре матрицы TF-IDF.
История выборов оформлена как два словаря: «нормализованный текст запроса —
объявления по частоте» и «текст плюс город — объявления по частоте»;
похожие запросы находятся той же TF-IDF мерой по текстам запросов
с порогом сходства 0.05. Списки объединяются поочерёдно с удалением повторов.

## 5. Проверка качества
Для локальной проверки обучающая выборка делится по группам «текст запроса,
город, категория»: фиксированное начальное число генератора 42, 500 групп
откладываются как проверочные. Релевантные объявления проверочной части
добавляются в корпус (без этого их там нет — пересечение обучения и корпуса
всего 5 процентов). Словари истории строятся только по оставшейся обучающей
части. Деление по отдельным строкам не применяется: при нём та же пара
«запрос — объявление» попадает и в обучение, и в проверку, и история даёт
завышенную оценку. Рост локального Recall@50 фиксировался в `experiments.md`:

| Этап | Проверочная оценка |
|---|---|
| BM25 по словам через пробел | 0.2434 |
| Добавлено упорядочивание по городу | 0.4121 |
| Добавлены основа слова и вес заголовка | 0.4685, затем 0.5007 |
| Несколько полей и TF-IDF (первая версия) | 0.6986 |
| Дополнение запроса словами из истории и увеличенные наборы | 0.7676 |
| Похожие запросы, TF-IDF по полному тексту и по буквам на коротком | 0.7792 |
| Дополнение словами из первых найденных и приоритет подкатегории (финал) | 0.7827 |

## 6. Найденные ошибки и исправления
1. Обрезка маленького набора по весу. Первая версия брала 200 кандидатов
   по одному весу — объявление на 500-й позиции терялось. Исправлено большими
   наборами (до 1200) и объединением нескольких списков.
2. Заголовок терялся в описании. Склейка одним текстом хоронит короткий
   заголовок поправкой BM25 на длину. Разделены полный и короткий поиски.
3. Редкие слова вырезались. Порог минимальной частоты 2 и предел словаря
   200 тысяч убирали редкие различительные слова хвостовых запросов.
   Порог снижен до 1, пределы подняты до 500 и 300 тысяч.
4. Буква «ё». Шаблон токенизатора без «ё» разрывал слова. Везде применена
   замена «ё» на «е» до токенизации.
5. История как готовые ответы почти не работала. Пересечение идентификаторов
   обучения и корпуса — 5.3 процента, точные записи из истории меняли 9 строк
   из 2452. Поэтому история дополнительно используется как текст: запрос
   дополняется словами из объявлений, которые раньше выбирали (покрытие
   дополнения — 436 из 500 проверочных запросов).
6. География фильтром вместо упорядочивания. Жёсткий фильтр даёт потолок
   0.818. Применён порядок «сначала свой город» без отбрасывания чужих.
7. Деление проверки по строкам. Даёт утечку пар «запрос — объявление»
   и завышенную оценку при использовании истории. Применяется деление
   только по группам.
8. Запросы из одного слова — слабейший отрезок (0.717 против 0.817 у запросов
   из трёх и более слов). Частично закрыты буквенными сочетаниями
   и дополнением запроса; остаток — синонимы без общих основ (3.5 процента
   пар), для них нужен семантический поиск.
9. Семантический поиск на центральном процессоре не уложился во время.
   Замер — около 10 объявлений в секунду, более пяти часов на корпус.
   Отложен как ночной эксперимент на графическом процессоре
   (черновик, в репозиторий не входит).

## 7. Воспроизводимость

Шаг 1. Скачайте данные архивом по ссылке из условия
(https://disk.yandex.ru/d/sNhfo0YOjGtufg) и положите три файла parquet
в папку `dataset/`. Проверьте, что файлы на месте:

```sh
ls dataset/
# train.parquet  benchmark_queries.parquet  benchmark_items.parquet
```

Шаг 2. Создайте окружение и установите зависимости:

```sh
python -m venv .venv
source .venv/bin/activate   # Windows: .venv/Scripts/activate
pip install -r requirements.txt
```

Шаг 3. Запустите построение ответа (около 30–40 минут):

```sh
python scripts/make_answer_v4.py
```
